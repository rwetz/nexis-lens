Nexis Lens: Design Document

A gesture-augmented viewer for presenting code, git diffs and markdown. Keyboard and mouse do everything; hand gestures are an optional extra layer.

2. Tasks

  1. Open a workspace: choose a local folder (or reopen a recent one) so its files and git state appear in the sidebar.
  2. Browse and read files: select files in the tree, scroll, search with Ctrl+F, and switch markdown between raw and preview.
  3. Review a git diff: view working-tree changes or a past commit, step through hunks, and choose unified or split layout.
  4. Switch tabs and use the session overview: move between open items or jump to any of them from a grid.
  5. Zoom and present: scale content for a room and enter presentation mode with the interface hidden.
  6. Enable and calibrate gestures: turn on the camera, set the tracking box, and arm gestures so hand movements control the app.
  7. Benchmark tracking in the Gesture lab: run a 10 second test of frame rate, latency and detection rate, then copy the results.

3. Prototypes

High-fidelity mock-ups per task, drawn to match the running app (dark theme). Multi-step tasks are storyboards: read the frames top to bottom. Each is explained with Shneiderman's Eight Golden Rules.

3.1 Open a workspace

Storyboard: 1a Welcome → 1b Pick folder → 1c Workspace loaded (or 1d error).

Eight Golden Rules

  • 1 Consistency: the one primary action (Open folder) uses the same filled button style used for primary actions everywhere else.
  • 2 Shortcuts: Ctrl+O opens the picker from anywhere; a recent workspace reopens in one click.
  • 3 Feedback: once loaded, the title bar shows the workspace name and branch pill, and the status bar shows the branch and commit.
  • 4 Closure: the flow ends in a loaded workspace whose empty stage says what to do next.
  • 5 Error handling: a failed open names the folder and the cause and offers "Choose another…".
  • 6 Reversal: Cancel in the picker changes nothing; opening another folder is always one shortcut away.
  • 7 User control: the user picks the folder; the app never scans the disk on its own.
  • 8 Memory load: recents show name and full path, so users recognise rather than retype.

3.2 Browse files and read code or markdown

Storyboard: 2a Markdown preview → 2b Code with find. Select a file in the tree, scroll, search with Ctrl+F, and flip markdown between Preview and Raw.

Eight Golden Rules

  • 1 Consistency: every file type shares the same tab bar, path bar and status bar; only the content area changes.
  • 2 Shortcuts: Ctrl+F to find, Ctrl+Shift+V for Preview/Raw, Ctrl+= / Ctrl+− to zoom.
  • 3 Feedback: the open file is highlighted in the tree and underlined in orange in the tab bar; find shows "3 of 12".
  • 4 Closure: the Preview/Raw toggle shows the active mode the moment it changes.
  • 5 Error handling: binary or unreadable files show a message in place of the content, not a blank pane.
  • 6 Reversal: Esc closes find; the toggle flips back; closing a tab never touches the file.
  • 7 User control: the viewer is read-only and never navigates on its own.
  • 8 Memory load: the full path stays visible above the content, and per-tab scroll and zoom are restored.

3.3 Review a git diff

Storyboard: 3a Working-tree change in split layout → 3b Past commit in unified layout. Both live in the Changes tab; history sits under the working tree.

Eight Golden Rules

  • 1 Consistency: added lines are green with "+", removed lines red with "−", in both layouts (never colour alone).
  • 2 Shortcuts: ] and [ step through hunks; Ctrl+Shift+U switches unified/split.
  • 3 Feedback: "Hunk 2/5", an orange marker on the current hunk, and +/− totals in the status bar.
  • 4 Closure: stepping past the last hunk should say so instead of silently stopping (proposed; not built yet).
  • 5 Error handling: a clean tree says "Clean — nothing to review"; a folder that isn't a repo says so.
  • 6 Reversal: the view is read-only, so nothing here can damage the repo; the layout toggle flips back.
  • 7 User control: the user chooses the file, the commit and the layout.
  • 8 Memory load: the status bar names the layout and, when armed, which gesture moves between hunks.

3.4 Switch tabs and use the session overview

Storyboard: 4a several tabs open → 4b Ctrl+G overview → Enter returns to the chosen tab.

Eight Golden Rules

  • 1 Consistency: the orange accent marks "current" in both the tab bar and the overview.
  • 2 Shortcuts: Ctrl+Tab / Ctrl+Shift+Tab, Ctrl+G, arrow keys and Enter.
  • 3 Feedback: the glowing card follows focus and carries a "current" badge.
  • 4 Closure: Enter closes the overview on the chosen tab.
  • 5 Error handling: with nothing open, the overview says so rather than showing an empty grid.
  • 6 Reversal: Esc returns to the tab you came from.
  • 7 User control: the overview opens only when asked for.
  • 8 Memory load: each card previews its content and full path, so tabs are recognised, not recalled; the key hints stay on screen.

3.5 Zoom and present

Storyboard: 5a zoom for the room → 5b F5 presentation mode with the chrome hidden.

Eight Golden Rules

  • 1 Consistency: the same zoom keys work in code, markdown and diffs.
  • 2 Shortcuts: F5, Ctrl+= / Ctrl+− / Ctrl+0, Ctrl+9 to fit; pinch when gestures are armed.
  • 3 Feedback: the zoom level appears next to the content and in the status bar.
  • 4 Closure: entering and leaving presentation mode is a single explicit action.
  • 5 Error handling: zoom is clamped to a minimum and maximum so text never vanishes.
  • 6 Reversal: Esc leaves presentation mode; Ctrl+0 resets zoom.
  • 7 User control: nothing enters presentation mode on its own.
  • 8 Memory load: a small "Esc to exit" hint stays visible while presenting.

3.6 Enable and calibrate gestures

Storyboard: 6a Settings → Camera, drag the tracking area → 6b Settings → Gestures, switch on → 6c back in the viewer, hold an open palm to arm.

Eight Golden Rules

  • 1 Consistency: every Settings page shares the same left navigation, rows and switch style.
  • 2 Shortcuts: Ctrl+, opens Settings; Ctrl+Shift+G turns gestures on or off without opening it.
  • 3 Feedback: live camera preview with the tracking area drawn on it; the HUD shows armed state, tracking and the last gesture.
  • 4 Closure: "Armed" and a green dot confirm gestures are live; each command flashes a short label ("Next hunk").
  • 5 Error handling: the HUD reports "Camera error", "No hand in frame" or "Low confidence" instead of guessing.
  • 6 Reversal: auto-disarm, a Disarm control and the shortcut switch it all off; the simulator lets people try gestures safely.
  • 7 User control: gestures are opt-in, need a deliberate arm step, and never block keyboard or mouse.
  • 8 Memory load: the bindings table lists every gesture, where it works and what it does.

3.7 Benchmark tracking in the Gesture lab

Storyboard: start the camera → run the 10 s benchmark → read the verdict and copy it as Markdown.

Eight Golden Rules

  • 1 Consistency: it is one more page in the same Settings window, with the same controls.
  • 2 Shortcuts: Ctrl+, then one click; one button copies the whole result.
  • 3 Feedback: live skeleton overlay, the recognised gesture with its confidence, and metrics during the run.
  • 4 Closure: after 10 s a verdict line states whether the target was met.
  • 5 Error handling: "Camera off" and a disabled Run button prevent a run with no camera.
  • 6 Reversal: Stop ends the camera at any time; a run can be repeated.
  • 7 User control: the user starts the camera and the run, and picks GPU or CPU inference.
  • 8 Memory load: "Copy as Markdown" replaces writing numbers down.

3.8 Gesture design

The gesture set is a design decision, not just a recogniser setting. The choices below follow the research summarised here, and every gesture still has a keyboard equivalent.

What the research says, and what we do about it

  • Midas touch (every movement becomes a command). Gesture interfaces need a way to separate intent from idle movement; the Gunslinger work [1] evaluates this directly. Decision: a deliberate arm step (hold an open palm), auto-disarm, and a cooldown on discrete gestures.
  • Gorilla arm (fatigue from holding the arm out). One paper [2] calls it a major barrier to long-term use. Gunslinger [1] uses an arms-down stance, and an elbow-anchored design [3] reports that people favour elbow and wrist motion. Decision: small movements in a draggable tracking box, relative (not absolute) palm motion, gestures meant for short bursts, and keyboard and mouse as the default.
  • Visible feedback. Gunslinger [1] shows a hand cursor that communicates posture, mode and tracking quality. Decision: the HUD shows armed state, the recognised gesture and tracking quality, and the tracking overlay can draw the hand skeleton.
  • Choose gestures people guess. Wobbrock's guessability method [4] shows users an effect, asks them to perform the cause, and keeps gestures many people agree on. Decision: familiar metaphors (drag the page, pinch to zoom, swipe to turn).
  • Camera limits. Webcam studies report accuracy falling with distance, dim light and cluttered backgrounds (for example [5]). Decision: target about 2 m, show a frame-rate check in Settings, and treat false positives as worse than misses.

Arming flow

Camera framing

Eight Golden Rules

  • 1 Consistency: the same gesture family means the same kind of action (swipe moves between things, pinch scales).
  • 2 Shortcuts: gestures are accelerators; every action also has a key.
  • 3 Feedback: the HUD, armed ring and tracking overlay respond to every recognised gesture.
  • 4 Closure: a short confirmation ("Next hunk") follows each discrete gesture.
  • 5 Error handling: low confidence is ignored rather than guessed; lost tracking shows a clear message.
  • 6 Reversal: opposite gestures undo each other (swipe left and right, pinch out and in); the fist toggles back.
  • 7 User control: the user arms gestures on purpose and can turn them off at any time.
  • 8 Memory load: nine gestures, each a familiar metaphor, listed in Settings.

How we will validate it

  • Run a short guessability test: show 5 to 8 people each outcome (for example "go to the next change") and record the gesture they try; keep the ones most people agree on.
  • Measure fps, latency and detection rate in the Gesture lab on target hardware.
  • Count accidental commands over five minutes of normal presenting (the roadmap's done criterion), and add recorded-landmark tests for each classifier.

How each gesture is recognised

MediaPipe returns 21 landmarks per hand. recognizer.ts first sorts each frame into one of five poses using finger geometry, then turns pose plus motion over time into events. Distances are divided by palm size (wrist to middle knuckle), so the thresholds hold whether the user is near the camera or far from it.

Only the highest-confidence ("primary") hand drives one-hand gestures, so two hands never fire twice. The dispatcher adds the safety layer on top: a confidence floor, the arming gate, auto-disarm after 4 s and a 450 ms cooldown between discrete commands.

4. Non-interface components

Critical system pieces behind the screens, and how each is implemented.

  • Shell and backend: Tauri v2 app (Rust backend, React 19 + TypeScript front end). Typed IPC calls connect the two; a browser-only mode serves an in-memory demo workspace.
  • Files: the Rust backend opens folders, lists files respecting .gitignore, and reads file contents on request.
  • Git: the backend runs the git CLI for status, diff, log and show; the front end parses unified diffs for the unified and split views.
  • Command bus: keyboard, toolbar and gestures all call runCommand(id, args, source); the active view handles it. This is why every task works without a camera.
  • Gesture pipeline: camera → MediaPipe HandLandmarker (WASM and model bundled under public/mediapipe/, no CDN, works offline) → recognizer (landmarks to poses to gestures) → dispatcher (confidence floor, arming, auto-disarm, cooldown) → bindings → command bus.
  • Performance plan: target at least 30 fps on an 8 GB integrated-GPU laptop. Profile in the Gesture lab; if short, drop to 480p, skip frames, or move inference to a worker with OffscreenCanvas.
  • Privacy and permissions: camera video is processed on-device and never uploaded; macOS builds include the camera entitlement and usage description.
  • Distribution: GitHub Actions builds Windows (NSIS/MSI) and macOS (universal dmg) installers from version tags.
